# Sherlock Home v0.5.0

## Milestone

v0.5.0 closes the current financial-ingestion and deterministic-enrichment milestone.

The release establishes a complete local pipeline from Santander statement parsing to idempotent PostgreSQL persistence, including configurable deterministic enrichment.

## Implemented pipeline

```text
Santander PDF
    ↓
pdftotext -layout
    ↓
Santander deterministic parser
    ↓
ParsedStatement / ParsedTransaction
    ↓
canonical statement normalization
    ↓
PostgreSQL merchant aliases
    ↓
merchant normalization
    ↓
transaction typing
    ↓
PostgreSQL category rules
    ↓
expense categorization
    ↓
SHA-256 fingerprint
    ↓
idempotent importer
    ↓
local PostgreSQL
```

## Financial semantics

### Transaction type

```text
expense
income
transfer
```

`transaction_type` describes the nature of a financial movement.

### Expense category

```text
food
groceries
transport
utilities
health
shopping
housing
financing
leisure
taxes
```

Only `expense` transactions are eligible for an expense category.

`income` and `transfer` remain uncategorized.

## Deterministic merchant normalization

Merchant extraction is conservative.

Known patterns may produce a normalized merchant. Unknown patterns remain unresolved rather than being guessed.

Merchant aliases provide deterministic canonicalization of merchant variants.

## Configurable local rules

v0.5.0 introduces PostgreSQL-backed runtime configuration:

```text
merchant_aliases
category_rules
```

Rules support explicit priority and enabled/disabled state.

Default category rules remain in code. Optional YAML category rules remain available for deterministic bootstrap/import scenarios, while PostgreSQL is the runtime configuration source intended for the future local web UI.

## Runtime orchestration

`app/services/financial_pipeline.py` centralizes the production-oriented enrichment path.

Callers no longer need to manually assemble merchant aliases and category rules for the normal runtime flow.

## Persistence

The transaction importer remains idempotent.

Derived fields such as:

```text
merchant
transaction_type
category
```

are persisted but intentionally excluded from transaction identity/fingerprinting.

Improving a deterministic enrichment rule must not create a duplicate source transaction.

## Test isolation

Persistence and rule tests use:

```text
sherlock_home_test
```

instead of the normal application database.

The pytest fixture fails closed if the configured test database matches the application database or does not use the `_test` suffix.

Mutable test tables are cleaned between integration tests:

```text
transactions
category_rules
merchant_aliases
```

## Security boundary

Protected financial data remains local.

The LLM is not trusted to:

- authorize operations
- calculate authoritative financial values
- invent merchant identity
- determine security policy
- directly manage database credentials
- bypass deterministic rule validation

## Next direction

The next product layer is expected to expose local configuration through authenticated API endpoints and, later, a local-network web interface over HTTPS.

That interface will manage PostgreSQL-backed merchant aliases and category rules without requiring household users to edit environment files directly.

## Post-v0.5.0 direction

API work starts after this checkpoint.

The next phase builds an authenticated `/api/v1` boundary for a single-household deployment model. Authentication, authorization, private HTTPS access, and API security tests are planned before configuration CRUD is exposed to the future web UI.

The project remains explicitly non-SaaS and non-multi-tenant.
